02 / Phân công chi tiết

Mỗi người một câu chuyện hoàn chỉnh

Ba pha Tấn công → Phòng thủ → Điều tra tạo thành vòng lặp khép kín. Phần điều tra không phải "làm thêm" mà là cách chứng minh bạn thực sự hiểu những gì mình vừa demo.

Người 1 · FTP

Sniffing plaintext & credential theft
01
🔴 Tấn công

Sniff FTP credentials & data

Dùng Wireshark/tcpdump bắt gói tin FTP plaintext trong lab. Trích xuất username, password và nội dung file truyền đi từ capture. Chứng minh FTP gửi mọi thứ dưới dạng cleartext.

  • File .pcapng chứa phiên FTP đầy đủ
  • Ảnh chụp filter Wireshark hiển thị USER/PASS/command
  • Bảng liệt kê thông tin nhạy cảm bị lộ
🟢 Phòng thủ

Chuyển sang FTPS hoặc SFTP

Bật TLS trên vsftpd (explicit FTPS) hoặc chuyển hẳn sang SFTP. So sánh cùng thao tác trước/sau: Wireshark không còn đọc được nội dung. Cấu hình ssl_enable=YES, force_local_logins_ssl=YES.

  • Cấu hình vsftpd trước và sau
  • PCAP "sau" chứng minh dữ liệu đã mã hóa
  • Test login thành công qua FTPS
🟣 Điều tra

Phân tích forensic trên PCAP đã bắt

Từ file capture ở pha tấn công: dựng timeline sự kiện (kết nối → login → lệnh → truyền file → ngắt), xác định chính xác thời điểm credential bị lộ, trích xuất file đã truyền bằng Wireshark Export Objects. Viết báo cáo điều tra ngắn: "Ai? Khi nào? Dữ liệu nào bị rò rỉ? Mức độ nghiêm trọng?"

Báo cáo: §2a + §4a + §6.1 + §ForensicsFTP

Người 2 · FTPS

TLS misconfiguration & downgrade attack
02
🔴 Tấn công

TLS downgrade / cert validation bypass

Trong lab: cấu hình FTPS sai (cho phép fallback plaintext, dùng cipher yếu, self-signed cert không verify). Demo client kết nối "FTPS" nhưng thực tế vẫn truyền plaintext do server chấp nhận non-TLS. Hoặc dùng openssl s_client chỉ ra cipher suite yếu (RC4, DES, TLSv1.0).

  • Transcript kết nối "FTPS giả" vẫn đọc được dữ liệu
  • Output openssl s_client hiện cipher/protocol yếu
  • Ảnh chụp cảnh báo certificate bị bỏ qua
🟢 Phòng thủ

Hardening TLS configuration

Cấu hình vsftpd: ssl_tlsv1_2=YES, ssl_tlsv1_3=YES, tắt TLSv1.0/1.1, chỉ cho cipher mạnh, require_ssl_reuse=NO (hoặc YES tùy ngữ cảnh), bật verify cert nếu dùng internal CA. Test lại: client không thể connect nếu không dùng TLS ≥ 1.2.

  • Cấu hình TLS hardened
  • Test nmap ssl-enum-ciphers xác nhận chỉ cipher mạnh
  • Kết nối thất bại khi cố downgrade
🟣 Điều tra

Audit log TLS negotiation failures

Phân tích vsftpd.log và auth.log sau pha tấn công: tìm các dòng "SSL connection failed", "Connection refused: SSL required", đếm số lần negotiate thất bại theo IP/thời gian. Xây dựng biểu đồ tần suất → phát hiện pattern tấn công downgrade. Viết timeline: attacker thử bao nhiêu lần, vào lúc nào, cipher nào bị reject.

Báo cáo: §2a + §4a + §6.1 + §ForensicsFTPS

Người 3 · SFTP / SSH

Brute-force & key-based hardening
03
🔴 Tấn công

SSH brute-force trên lab

Dùng Hydra/Medusa (chỉ trên VM lab!) thử dictionary attack vào SSH user yếu. Ghi nhận số lần thử/thành công, thời gian crack. Đồng thời demo weak password policy: user dùng pass "123456" bị chiếm trong vài giây.

  • Log brute-force: số attempts, thời gian, kết quả
  • Auth.log chụp failed passwords liên tiếp
  • Screenshot tool tấn công (blur sensitive info)
🟢 Phòng thủ

Key-only auth + chroot + Fail2ban

Tắt password auth (PasswordAuthentication no), bật Ed25519 key-only, cấu hình chroot jail cho SFTP user, cài Fail2ban ban IP sau N lần fail. Test: key hợp lệ vẫn vào, password bị từ chối, brute-force bị ban.

  • sshd_config trước/sau
  • Fail2ban status + jail config
  • Retest: legitimate access OK, attack blocked
🟣 Điều tra

Forensic analysis trên auth.log

Từ auth.log thu được: trích xuất tất cả failed attempts, group by source IP, tính frequency/timing pattern. Xác định top offending IPs, thời gian cao điểm tấn công, username bị nhắm nhiều nhất. So sánh trước/sau Fail2ban: số attempts giảm bao nhiêu %, ban events xảy ra khi nào. Viết incident report ngắn.

Báo cáo: §2a + §4a + §6.3/6.6 + §ForensicsSSH/SFTP

Người 4 · SMTP

Open relay abuse & spam prevention
04
🔴 Tấn công

Exploit open relay (lab isolated)

Cấu hình Postfix sai (mynetworks quá rộng, thiếu smtpd_recipient_restrictions). Từ máy khác trong lab, gửi mail đến domain ngoài (.test) → server chấp nhận relay. Chứng minh attacker dùng server làm spam relay. Capture transcript 250 OK cho recipient ngoài.

  • Transcript SMTP relay thành công (250 OK)
  • mail.log showing relay abuse
  • Sơ đồ luồng mail bị exploit
🟢 Phòng thủ

Close relay + enforce AUTH/TLS on 587

Thu hẹp mynetworks, bật smtpd_recipient_restrictions reject_unauth_destination, yêu cầu SASL auth trên port 587, bật STARTTLS. Retest: relay ngoài bị reject (554), gửi nội bộ qua 587+AUTH vẫn hoạt động.

  • main.cf trước/sau
  • Transcript 554 Relay access denied
  • Gửi mail nội bộ TLS+AUTH thành công
🟣 Điều tra

Mail queue forensics & log correlation

Từ mail.log: truy vết queue ID của các mail relay trái phép, xác định nguồn IP, timestamp, recipient list. Đếm volume mail bất thường/giờ so với baseline. Correlate với auth.log (có login hợp lệ nào bị chiếm?). Xây dựng timeline cuộc tấn công relay và viết short incident report.

Báo cáo: §2b + §4b + §6.9/6.11 + §ForensicsPOSTFIX

Người 4 · POP3 / IMAP

Plaintext auth & mailbox exfiltration
04+
🔴 Tấn công

Sniff POP3/IMAP credentials & pull mailbox

Kết nối POP3 (port 110) / IMAP (port 143) plaintext trong lab. Bắt gói → trích xuất user/pass. Sau khi có credential, dùng client kéo toàn bộ mailbox về máy attacker (data exfiltration). Với IMAP: demo SELECT INBOX + FETCH toàn bộ messages.

  • PCAP chứa POP3/IMAP plaintext session
  • Ảnh captured credentials
  • Screenshot mailbox bị exfiltrate
🟢 Phòng thủ

Enforce POP3S (995) / IMAPS (993) + disable plaintext

Dovecot: ssl = required, disable_plaintext_auth = yes, cấu hình TLS cert, tắt port 110/143 hoặc redirect lên 995/993. Test: openssl s_client verify TLS, client Thunderbird kết nối IMAPS thành công, plaintext bị reject.

  • doveconf output before/after
  • openssl s_client test on 993/995
  • Plaintext connection rejected log
🟣 Điều tra

Detect mailbox exfiltration via Dovecot logs

Từ Dovecot auth/mail log: tìm sessions login từ IP lạ, đếm số FETCH/RETR commands bất thường (volume spike), so sánh bytes transferred vs baseline. Phát hiện dấu hiệu "kéo sạch mailbox": nhiều RETR liên tiếp + logout ngay sau đó. Timeline: credential bị lộ lúc nào → mailbox bị exfiltrate lúc nào → bao nhiêu mail bị lấy.

Báo cáo: §2b + §4b + §6.2 + §ForensicsDOVECOT

03 / Quy trình demo thống nhất

5 bước cho mọi demo — kể cả điều tra

So với bản cũ (4 bước), bản mới thêm bước 5 "Điều tra forensics" để biến mỗi demo thành một case study hoàn chỉnh.

01

Ghi nhận trạng thái yếu (baseline)

Chụp cấu hình hiện tại, cổng đang mở, user/file giả, snapshot VM. Nói rõ đây là mạng Host-only/Internal. Đây là "hiện trường gốc" để đối chiếu sau này.

Ảnh + config "trước"
02

Thực hiện tấn công có kiểm soát

Đúng 1 kịch bản: sniff FTP, downgrade TLS, brute-force SSH, exploit open relay, hoặc exfiltrate mailbox. Lưu toàn bộ bằng chứng: PCAP, transcript, log — đây là nguyên liệu cho bước 5.

PCAP / transcript / log
03

Áp dụng biện pháp phòng thủ

TLS, key-only, chroot, relay restriction, disable plaintext auth... tương ứng dịch vụ. Ghi lại mọi thay đổi cấu hình (diff trước/sau).

Config "sau" + diff
04

Kiểm thử lại (retest)

Chứng minh: nguy cơ đã bị chặn + người dùng hợp lệ vẫn hoạt động bình thường. Nêu giới hạn: biện pháp này chưa xử lý được gì.

Bảng trước / sau
05

🔍 Điều tra forensics trên bằng chứng đã thu

Quay lại PCAP/log/transcript từ bước 2. Dựng timeline, trích xuất artifacts, tính metrics (frequency, volume, entropy), viết incident report ngắn. Đây là phần chứng minh bạn hiểu chứ không chỉ chạy lệnh.

Timeline + report
